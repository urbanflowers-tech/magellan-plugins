# Review response — Magellan WordPress v3 alpha.5

9 October 2026. Reviews were treated as suggestions and checked against the actual plugin and paired Magellan receiver. They did identify defects. They did not establish that the plugin was production-certified, nor did our previous local checks establish that.

Magellan still owns inventory, canonical orders, financial state, reporting and autonomous operations. This update changes the website evidence collector and its legacy compatibility path. It adds no WordPress stock or finance engine.

## Findings and decisions

| Finding | Assessment and action |
|---|---|
| Tax-inclusive WooCommerce amounts fail capture | Confirmed. Decimal string arithmetic now rounds half-up to the currency exponent, handles scientific notation from computed cart floats, and uses unfiltered stored decimals where WooCommerce supports them. Real 7% inclusive-tax cart/order cases are tested. Raw WooCommerce values remain at the source and are available to Magellan's existing REST importer; the wire money schema remains compatible. Invalid/nonfinite amounts still fail visibly; we never manufacture a zero amount to make a financial observation pass. Independently rounded line values need not sum exactly to a separately rounded order total. |
| One missing receipt delays the store | Confirmed. Missing/invalid per-event receipts only back off those rows. A network error, HTTP 429 or 5xx can delay transport for the store. A new healthy event can deliver while an older event waits. |
| A bad order stalls reconciliation / only 600 orders per day | Confirmed. A durable recovery table tracks failed source orders separately. The scan advances, up to 100 orders per invocation with a five-second budget checked between pages, plus up to 10 due recovery orders; queued continuations handle backlog. This is a bounded work target, not a strict wall-time ceiling for an exceptionally large order. |
| Capture-gap warning is permanent | Confirmed. It now has a stable ID/count and an explicit CLI review/acknowledgement command. Failed source captures must be resolved before acknowledgement. Lost cart transitions are not declared recovered merely because a scan completed. |
| Erasure permanently blocks commerce and misses related events | Confirmed. Erasure finds related order/status/payment/refund/cart evidence, including older events without entity keys. Bounded processing removes local identifying bodies, recaptures order/refund source evidence without analytics links, and gives retained status/payment observations new event IDs. Old IDs are never sent with changed bodies. Magellan's tombstones handle already delivered/in-flight evidence. Intake acceptance is not proof of completed erasure. |
| Delivered rows and optional carts consume capacity | Confirmed. Cleanup runs on drains and five-minute maintenance, prunes up to 1,000 accepted rows per pass, and reclaims accepted bodies early under pressure. Optional observations stop at 40,000 rows/80 MiB, ordinary commerce at 49,000/~98 MiB, leaving the final reserve for privacy. There is no production throughput claim. |
| Dead letters / installation rebind need a recovery tool | Confirmed. Added paginated JSONL queue export and explicit single-event discard with typed event-ID confirmation. Unacknowledged evidence remains retained until resolved or deliberately discarded; it is not silently deleted to make the queue appear healthy. Installation rebinding still refuses unresolved rows. |
| Action Scheduler compatibility and maintenance runner | Addressed. Declared minimum WooCommerce is now 9.9, with explicit scheduled-job checks and unique scheduling. V3 maintenance uses Action Scheduler when available, with WP-Cron fallback. Tests exercise one queued drain after a capture burst and its successor after completion. Legacy cron still requires its existing WP-Cron runner. |
| Extra database lookup after every AS action | Confirmed. The supplied action is inspected at `after_execute`; only our action ID is remembered until `completed_action`. Moving scheduling directly to `after_execute` would run before AS marks the action complete and could lose the successor. |
| Status totals scan every payload | Confirmed. Byte usage comes from quota reservations. State counts still use the indexed outbox table. |
| Full-to-pilot mode does not restore legacy jobs / reactivation restores obsolete jobs | Confirmed. The mode-aware legacy scheduler restores missing jobs when entering measurement-only mode and does not schedule them when full v3 is active. The unused daily-cleanup hook is removed. |
| Long paid landing event disappears | Confirmed. Optional UTM evidence is shortened to fit before immutable event bytes are created. Duplicate raw click IDs can be omitted from the current touch when retained in entry evidence; if necessary raw IDs are omitted whole while their types remain. Click IDs are never truncated into different identifiers. The 4 KiB event budget and existing receiver schema remain unchanged. |
| Checkout scripts miss jQuery or template-rendered Blocks | Confirmed. The checkout adapter declares jQuery and wp-api-fetch dependencies on checkout pages, including when the block comes from a theme template. |
| Legacy cookie on `.co.th` and encoding | The public-suffix cookie failure was already known and is now fixed with host-only secure cookies. Cookie values are percent-encoded; the PHP reader tolerates older plus-to-space transport. We did not verify the review's claim that “most” old cookies failed to decode. |
| Legacy pixel assumes consent | Confirmed. Both pixels now use explicit consent/initial state and the Cookiebot adapter. Unknown/denied analytics creates no legacy tracking identity. Withdrawal clears both pixels' identifiers; GPC prevents advertising grant. Legacy checkout email capture waits for analytics consent, and server payloads no longer default to granted. Operational order delivery remains available without analytics consent. Consent integration on the real merchant site still needs verification. |
| Legacy missed-order retry is defeated by `_mgln_event_scheduled` | Confirmed. Deduplication checks actual pending/running jobs and successful delivery instead of an orphaned metadata flag. Lost scheduled work can be queued again. |
| Legacy URL security / public route IP / health display | Confirmed. Signed legacy transport and bootstrap require public HTTPS and disable redirects; returned configuration is checked before it is saved. Rate limiting uses the connection IP rather than arbitrary forwarded headers. The health display reads the field actually emitted by the plugin, including zero. |
| Historical identity sync loads the whole site and includes subscribers | Confirmed. It now processes one 100-record page per invocation with a durable retry cursor; subscriber-only accounts are excluded. It remains the legacy customer import, not a new v3 identity graph. Delivery failures retain the current page. |
| No uninstall retention choice | Confirmed. An authenticated admin preference chooses whether uninstall retains local v3 queue/diagnostic data or deletes it. Retain is the default; credentials are removed in either case. WooCommerce orders and Magellan records are unaffected. Per-site behavior is tested; multisite network uninstall is not certified. |
| The install ZIP lacks tests/handoff | Tests belong in the source/review bundle, not the installed runtime. The handoff is now also included in the install ZIP, and the source contains runnable regressions and saved results. |
| Measurement-only sends observations twice, therefore creates duplicate orders | The first part is intentional coexistence. The conclusion does not follow: the paired backend explicitly skips v3 canonical order import and operational cart projection in measurement-only mode. Keep this as a controlled pilot and review when to retire the old feed. |
| Cart conversion should wait for payment | Not adopted. `cart_converted` means an order was created. Payment failure, cancellation and settlement are separate evidence/state. Magellan must distinguish an unpaid order from an abandoned pre-order cart; changing this event to mean payment would corrupt the agreed contract. |
| V3 order observations omit customer/address data | Intentional. The paired full-mode receiver fetches the source WooCommerce order through the existing authenticated REST connection and canonical importer. Measurement-only links observations to orders imported by the existing feed. Live connection readiness still needs verification. |
| `tracking_started_at` is null | Intentional. Installation is not proof that browser measurement reached reports. Magellan derives actual start/coverage from accepted/applied evidence; the local plugin does not invent it. |
| PHP/JS reserialization may invalidate receipts | This is a real integration concern already covered by shared PHP byte/hash fixtures and the receiver parser. Alpha.5 fixtures are checked against that same receiver contract. |
| Challenge response is not separately HMAC signed | Correct observation, not a demonstrated authentication bypass. The request is HMAC signed; the response is authenticated by validated HTTPS, bound to the fresh challenge and installation/site/environment/mode. There is no specified response-signature contract to invent independently on the plugin. |
| Updater skips alpha/prerelease tags | Intentional. Alpha builds require explicit installation. The automatic stable updater must not promote an unapproved pilot to all stores. |

## Release status

This is a new plugin review candidate. The old `v3.0.0-alpha.4` tag remains immutable. The matching backend measurement-only patch is unchanged; do not assume it has been deployed because the plugin has a GitHub tag.

The prior backend run had nine unresolved broader test failures, reproduced on its unchanged parent. This plugin update does not resolve or erase that result. Real storefront/CMP/payment-provider checks, actual ingestion/report application, Rio's exact-candidate release review and the reviewed rollback remain necessary before live activation. No production or staging site was changed by this review.

## Verified alpha.5 checks

488 WordPress/WooCommerce checks across four runtime/storage combinations, 27 browser checks, 31 coexistence browser checks, 22 resilience checks, 206 cross-language checks, and 292 fixtures through both the plugin schema and actual paired receiver validation. All passed. Syntax checks passed for 25 PHP and seven JavaScript files. These checks use isolated fixtures, not live shoppers or actual payment-provider transactions.
